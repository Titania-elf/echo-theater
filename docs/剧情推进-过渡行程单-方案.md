# 剧情推进 · 过渡行程单 — 方案

> 设计定稿 2026-10-15。本文件是实现前的权威设计记录；落地过程中若有偏离，以改动同时更新本文件为准。

## 1. 问题与根因

**症状**：剧情推进给出的三条候选永远朝"下一个大纲条目"推进。实测中玩家刚聊了一楼，候选就已经是"一周后……"——直接跳到下一个阶段，中间没有任何过渡剧情。

**根因不是模型贪快，是大纲中间没有东西可写**：

1. 候选被钉死在大纲条目的粒度上。rolling 模板要求每条候选带 `item_index`，而进度就是这个整数指针 `plan.progress.itemIndex`（`storyOutlineWindow.js`）。"推进"在实现上等于"把 item_index 加一"。
2. 大纲条目之间是空的。条目1「开场当晚」、条目2「一周后」——模型判 current=1，候选被要求"推进"，那除了写"一周后"它无路可走。模板里那句"不要用候选来跳过中间情节"是句空话，中间没有情节可跳。
3. 同一个问题**盲盒模式已经解过**：`nodes[] → events[]` + `{{eventsPerGap}}`，节点是硬锚、事件是垫脚石。本方案就是把这层垫脚石搬到普通大纲模式。

## 2. 目标与玩家体验

给**当前所在的 gap** 按需生成一份**有序的过渡行程单**（几步关键事件），推荐剧情的锚点从"大纲第 N 条"变成"过渡段第 K 步"。骨架（行程单）＋血肉（候选）各司其职：

- 行程单定"走到哪"——玩家自己写一句这段的用意，模型排成 N 步，可增删改序。
- 候选定"怎么走"——点某一步后，推荐剧情产出 2~3 条**专门演这一步**、可直接发送的输入。

**与既有机制并存，不取代**：没有行程单时一切照旧（普通推进）。盲盒模式不受影响。

## 3. 数据模型

普通方案（`getPlanKind` 归为 normal）新增**可选**字段，老方案没有 → 空表，**不设 schema 版本**（全仓惯例是 tolerant read + normalize-on-write）：

```
plan.transitions = [
  {
    fromIndex,    // 0-based 大纲条目下标；toIndex 恒为 fromIndex + 1，不单独存
    brief,        // 玩家填的"这一段大概怎么走"
    events: [ { title, span, brief } ],   // 有序，玩家可增删改序
    cursor,       // 已走完的事件数，0..events.length
    generatedAt,
  }
]
```

- **激活判定**：`transitions.find(t => t.fromIndex === progress.itemIndex)`。`itemIndex` 一旦走到 `fromIndex + 1`，该段自动失活——不需要显式归档；回退到 `fromIndex` 时又会自动复活，`cursor` 原样保留。
- `cursor === events.length` ⇒ 整段走完，终点行点亮、可以跨段。
- 纯逻辑在 `src/core/transitionPlan.js`（无宿主依赖，可被单测直接 import，同 `blindboxPlan.js`）；持久化在 `storyOutlineWindow.js` 的 `setPlanTransition` 一族，与 `setPlanProgress` / `setPlanCandidates` 同分工。

**为什么 cursor 不放进 `plan.progress`**：那样 `setPlanProgress` 那个白名单字面量也得改，而 cursor 天然属于"这一段"。放在 transition 自己身上，`plan.progress` 结构一字未动。

## 4. 契约变更：rolling 模板 v1.6 → v1.7

候选新增 `step_index`（本候选走完后过渡段内已完成几步）。这是**契约变更**，两处必须同步，否则用户存着的 1.6 模板会继续按旧契约要求模型，解析出来全是 `null`，行程单等于白做：

1. 默认模板：新增核心原则 6（有行程单时推进单位是"一步"而非"一条"，`item_index` 不得越过本段）、硬性要求 7（`step_index` 怎么填）、user 段新增 `{{transitionContext}}`、version 提到 `"1.7"`。
2. `getPromptTemplates()` 的 legacy 探测链补一档：`!sys.includes("step_index")` ⇒ 重置为默认并 `console.info`。与既有的 1.3/1.4/1.5 同构。

**step_index 的语义**（0..N，N = 行程单步数）：`0` ＝ 就地深化、不推进过渡；`k+1` ＝ 把第 k 步演完；`N` ＝ 过渡全部走完、下一步即跨段。**没有行程单时一律 `null`**。

> ⚠ `null` 与 `0` 在这套数据里语义完全不同，而 `Number(null) === 0` 是有限数——两处解析都必须显式挡掉（`parseRecommendationResponse` 与 `normalizeCandidate`）。读错会让"没有行程单"变成"第 0 步"，点候选时把 cursor 打回原点。

## 5. 生成（第 6 类提示词模板 `transition`）

下单输入：**过渡梗概**（自由文本，玩家填）+ **事件数量**（默认 4，夹 1~10）。gap 由进度指针决定——只服务**当前所在的那一段**。

模板要点：恰好 N 条、按时间先后；`span` 沿时间轴单调前进且累加不超过本段跨度；`brief` 用梗概体（文风硬约束同其它模板）；上一步的后果驱动下一步；第一条承接最近正文的最后状态，最后一条落在下一条的入口。变量：`{{gapPair}} {{gapBrief}} {{eventCount}} {{recentChat}}`。

- 走 `runGenerationFlow`（拿 raw 历史与可编辑修复弹窗），`resolveOpening: getRollingOpeningText` 绕开「选择参考来源」对话框。
- 采样参数**复用 `scenes` 组**，不新增模块键。
- `from_index` 由调用方给定、不信模型自报；事件条数按 `eventCount` 截断；零有效条目抛错 → 修复弹窗。
- 解析器 `parseTransitionResponse` 导出供单测（同 `parsePacingResponse`）。

**「点某一步」不是发送**：行程单的 `brief` 是**面向作者**的梗概体，不是可直接发送的玩家输入（候选才是）。所以点一步的语义是**定位**——`cursor = k`，并清掉上一步遗留的候选（它们已过期，留着点了会推进到错误的步）。生成仍走既有的「推荐剧情」按钮（有行程单时文案改成「推荐这一步的剧情」）。

**刻意不做"点一步就自动生成"**：那是一次隐式 API 调用，点错一下白烧一次；仓库既有风格也是显式按钮（「分析节奏」）。

## 6. 跨段闸门（唯一一处刻意加的夹紧）

`applyProgressFromModel` 在写回模型判断的 `item_index` 时，若当前 gap 有激活行程单且 `cursor < events.length`，把写回值**夹在 `fromIndex`**。

理由：每次生成候选都会回写模型判断的进度。模型完全可能判出"已经跨过去了"，指针一跳、行程单立刻失活——玩家刚排好的清单凭空消失，等于白排。

两条边界：

- **只夹跨段，不夹段内推进**：`cursor` 由 `setSceneStep` 直接赋值、可进可退，与 `applyProgressFromModel` 注释里"可进可退、判断权交给模型"的既定设计一致。
- **不拦玩家的显式操作**：`crossSceneGap` 先把行程单标成走完（等于"跳过剩下几步"）再推指针。闸门是拦模型自作主张的，不是拦人的。

**大纲重生成时清空整表**（`applyParsedOutline`）：路标重画 ⇒ 每段 gap 的起讫都变了。

## 7. 前端表现

面板「推荐剧情」页，在进度块与候选列表之间内嵌 `buildTransitionHtml`：

- **本段还没排**：折叠块（标题行兼作开关，整块只占一行），展开后是梗概文本框 + 事件数 + 「生成行程单」。
- **已排**：有序清单，已完成置灰打勾、当前步高亮、终点行「→ 进入「下一条」」（走完才点亮成实线）。底部「编辑 / 重新生成 / 删除」；编辑态下每步可改文字、增删、上下移。
- 顶部进度追加子进度「本段过渡 2 / 4 步」；折叠态横条也从 extData 现读并显示（那条路径刻意不加载大纲模块，逻辑与 `transitionPlan` 同义但不引它）。
- 候选卡片小字改成「停留在第 N 条 · 走完过渡第 K / M 步」。

**编辑期不落盘**：编辑态持一份 `transitionEditDraft`（模块级，ST 重渲染也不丢），所有增删改序只改草稿、重绘从草稿读；退出编辑或收起面板时才一次性提交。原因是落盘要过 `normalizeTransition`，而它会丢掉 brief 为空的条目——编辑中清空一条 brief 再点"上移"，那条会当场蒸发。

**编辑框「输入即写草稿」**：文字改动由 `input` 处理器实时回写草稿（只同步变量、不重绘，避免丢焦点）。

> ⚠ 别改成"等失焦/等结构操作时再从 DOM 捞一遍"。用户改完字直接点「完成编辑」或终点行时，不会再有任何一次读取，刚打的字会静默消失——这是这套交互最容易踩的坑，已在单测里用源码断言锁住（`不该再有 flushTransitionEditDraft 这条补丁路径`）。

**空行程单等于没有**：玩家把事件删光后整段丢掉，不留 `0 / 0 步` 的空壳（`isTransitionDone` 会把空表当已走完，那是个既拦不住跨段、又占地方、还回不到下单表单的死状态）。

## 8. 与既有系统的复用关系

- 提示词链、生成流、修复弹窗、raw 历史：全走既有 `runGenerationFlow`。
- 解析器导出供测：同 `parsePacingResponse`。
- 面板：沿用 `tsa-` 前缀、委托事件绑定、「输入时只同步变量不重绘」的焦点保持手法（同 `#tsa-pacing-directive`）。
- 与节奏把控、盲盒导演**正交**：各占各的注入键、各读各的状态。

## 9. 已知边界

- 只管**当前进度所在的那一段**，不能提前给后面的 gap 铺路（提前排的会因剧情跑偏而作废）。
- 行程单是**手动挡**：没有后台判定自动推进 cursor（对比盲盒导演）。玩家自由输入跳过某一步时，cursor 不会自动跟上——模型下一轮靠正文判断，指针另有跨段闸门兜着。
- 封装层不加密：`plan.transitions` 与其它方案数据一样存在用户自己的 extData 里。
- `api.js` 与 `sceneAdvanceBubble.js` 无法被测试夹具模块化加载（多段宿主 import），面板侧只做到「整个模块能加载」的冒烟测试 + 源码文本断言。
